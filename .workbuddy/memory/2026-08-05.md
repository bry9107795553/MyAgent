## 启动与暴露 (start.sh + rc-tunnel)
- 三端口健康检查全通: 8000 返回 Qwen2.5-14B 模型 JSON、8080 返回 {"status":"ok","llm_available":true}、80 返回 HTTP 200 → 服务 100% 跑起来。
- rc-tunnel 默认未安装: 先 `/var/run/secrets/frp-self-service/install`（装到 /root/.local/bin/rc-tunnel）。注意该目录不在默认 PATH，需先 `export PATH="$HOME/.local/bin:$PATH"` 才能用 rc-tunnel 命令。
- 关键坑: rc-tunnel 0.3.0 要求 `--port` 必须 ≥1024（报 `port must be between 1024 and 65535`），不能直接暴露 80。
- 修复: 给 Nginx 加高位监听端口 8088（sed 在 `listen 80;` 后插入 `listen 8088;`），`nginx -s reload`，再 `rc-tunnel expose --port 8088` 拿公网网址。网页内容与 80 完全一致。
- rc-tunnel expose 是前台阻塞/常驻命令，用 `nohup ... &` 后台跑，URL 从 /tmp/rc-tunnel.log 读。隧道空闲 60s 回收，需重新 expose。
- 验证 `rc-tunnel expose --help`: 仅 `-port`(Notebook localhost port) 与 `-prefix` 两参数，无 target/内部端口映射能力 → 确认 8088 nginx 监听是 rc-tunnel 0.3.0 下暴露 Web UI 的唯一正解（用户曾质疑此 workaround 是否错，已用 --help 证据澄清）。
- 踩坑: 第一次 expose --port 8088 在 nginx 还没监听 8088 时跑的 → 浏览器开网址出现 frp 自带 404 ("page not found, powered by frp")，即 frp 路由不到本地服务。修复: 先确认 `curl localhost:8088`=200，再 `rc-tunnel stop` + 重新 `expose --port 8088`(此时 8088 已活，frpc 注册正常)。注意 stop 后旧域名前缀进入 quarantine 不能复用，新 expose 会换一条新 URL，必须用新 URL。

## 致命 bug: 网页"空壳"、点不了发送、智能体列表空白
- 症状: 网页能开(静态文件正常)，但左侧 AGENTS 面板空、发不了消息，看似"没连后端"。
- 排查: 直连后端 8080 时 /api/agents、/api/layout、/api/skins、/api/health 全部 HTTP 200 + 真 JSON → **后端 100% 健康**，问题在 Nginx 这层。
- 根因: nginx.conf 有 `location /api/agents/ { ... }`(带斜杠)。Nginx 对请求 `/api/agents`(无斜杠)自动 301 重定向补斜杠；默认 `absolute_redirect on` 使 Location=绝对网址 `http://localhost:8088/api/agents/`。浏览器在自己电脑上跟随此 301 去请求自身 localhost:8088 → fetch 失败 → 智能体列表空 → 没选中 agent → sendMessage 静默 return(看起来点不了发送)。/api/health 不重定向所以指示灯亮，正是迷惑点。
- 修复: 在 nginx.conf server 块加 `absolute_redirect off;`，使 Location 变相对 `/api/agents/`，浏览器按当前页公网网址补全 → 经隧道回云端 → 200。已同步修复仓库版 nginx.conf(在 server_name localhost; 后插入)。
  - 应用命令: `sed -i 's|        server_name localhost;|        server_name localhost;\n        absolute_redirect off;|' /etc/nginx/nginx.conf && nginx -s reload`
- 关键点: 聊天 WebSocket 用 `location.host` 拼地址(ChatView.vue:136 `${protocol}://${location.host}/api/agents/${id}/ws`)，主机就是公网网址，不受此重定向 bug 影响 → 修好重定向后 agents 面板填充、选 agent、发送、WebSocket 全链路应一次通。
- **修正**: `absolute_redirect off;` 在这台实例的 nginx 上加了、reload 也成功(nginx -t 通过、grep 第30行确认存在)，但 `/api/agents` 的 301 Location 仍是绝对 `http://localhost:8088/api/agents/`，说明该 nginx 版本此重定向不吃 `absolute_redirect off`。**改用更彻底方案**：在 nginx.conf 插入 `location = /api/agents { proxy_pass http://127.0.0.1:8080; ... }` 精确匹配块，从源头消除 301（请求直接代理，不再补斜杠重定向）。并 `pkill -TERM nginx; sleep 1; nginx` 硬重启确保新配置加载(reload 疑似未生效)。验证: `curl /api/agents` 不再有 Location 头、HTTP 200、返回智能体 JSON(`general_assistant`)。**此精确匹配块已同步写回仓库 nginx.conf**，作为未来部署的真正修复(absolute_redirect off 保留为辅助)。
- 状态: 截至本会话末，云端实例 `/api/agents` 已能正常返回智能体列表(HTTP 200 + JSON)。下一步用户在浏览器 F5 刷新公网网址、确认 AGENTS 面板出现"通用助手"并能发送消息对话，即全链路打通收工。
